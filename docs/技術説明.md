## 🎯 データの流れ 3パターン徹底解説

### パターン1: サーバーコンポーネントで直接データ取得

**使用例**: 現在は未使用（page.tsx は認証チェックのみ）

```typescript
// app/dashboard/page.tsx (サーバーコンポーネント)
export default async function DashboardPage() {
  // ✅ サーバー側で実行される
  const session = await auth();

  // 🔹 理論上はここでデータ取得可能
  // const clips = await prisma.clip.findMany();
  // return <DashboardContent clips={clips} />;

  // ❌ 現在は認証チェックのみで、データは渡していない
  return <DashboardContent userId={session.user.id} />;
}
```

**メリット**:
- サーバー側で実行されるため、データベースに直接アクセス可能
- 初期レンダリング時にデータが含まれるため、SEO に有利
- クライアント側の JavaScript を削減できる

**デメリット**:
- ページ全体の再レンダリングが必要（ページ遷移時）
- インタラクティブなUI（ボタンクリック、検索等）には不向き
- リアルタイム更新には向かない

**なぜこのプロジェクトでは未使用？**:
- クリップデータは頻繁に更新され、リアルタイム性が求められる
- ユーザーがお気に入り追加/削除したら即座にクリップ一覧を更新したい
- 検索・ソート機能があるため、クライアント側で状態管理が必要

---

### パターン2: サーバーアクション (Server Actions)

**使用場所**: `actions/user.ts`, `actions/favorites.ts`

```typescript
// actions/user.ts
'use server';  // ← このディレクティブが重要！

export async function updateDisplayName(name: string) {
  // ✅ サーバー側でのみ実行される
  const session = await auth();

  // データベース更新
  await prisma.user.update({
    where: { id: session.user.id },
    data: { name },
  });

  // キャッシュ再検証
  revalidatePath('/settings');

  return { success: true };
}
```

```typescript
// クライアント側から呼び出し
'use client';

import { updateDisplayName } from '@/actions/user';

function SettingsForm() {
  const handleSubmit = async () => {
    // 🔹 関数として直接呼び出すだけ！
    const result = await updateDisplayName(newName);
    if (result.success) {
      alert('更新成功！');
    }
  };
}
```

**理由**: データベース更新処理はサーバー側で安全に実行したい

**メリット**:
- API Routes を作らなくても、サーバー側処理を呼び出せる
- 関数のように簡単に使える（fetch() 不要）
- 認証・バリデーションをサーバー側で完結できる
- `revalidatePath()` でキャッシュ管理が簡単

**デメリット**:
- POST リクエストのみ（GET 不可）
- データ取得には向かない（更新処理専用）
- エラーハンドリングが少し複雑

**使用例**:
- ✅ ユーザー表示名変更
- ✅ お気に入り配信者追加/削除
- ✅ アカウント削除
- ❌ クリップ一覧取得（これは API Routes で行う）

### パターン3: API Routes

**使用場所**: `app/api/clips/favorites/route.ts`

```typescript
// app/api/clips/favorites/route.ts
export async function GET() {
  // ✅ サーバー側で実行される
  const session = await auth();

  // お気に入り配信者を取得
  const favorites = await prisma.favoriteStreamer.findMany({
    where: { userId: session.user.id },
  });

  // 各配信者のクリップを Twitch API から取得
  const clips = await getClipsByBroadcaster(favorite.streamerId);

  return NextResponse.json({ data: clips });
}
```

```typescript
// クライアント側から呼び出し
'use client';

function DashboardContent() {
  const fetchClips = async () => {
    // 🔹 fetch() で API を呼び出す
    const response = await fetch('/api/clips/favorites');
    const { data } = await response.json();
    setClips(data);
  };
}
```

**理由**: クリップデータは外部 API（Twitch）から取得するため、サーバー側で処理

**メリット**:
- GET/POST/DELETE など、すべての HTTP メソッドが使える
- データ取得に最適
- キャッシュコントロールが細かく設定可能
- 外部 API（Twitch）との連携に向いている

**デメリット**:
- サーバーアクションより少し記述が多い
- fetch() を使うため、エラーハンドリングが必要
- キャッシュ管理は手動で行う必要がある

**使用例**:
- ✅ お気に入り配信者のクリップ取得
- ✅ 配信者検索
- ✅ いいねしたクリップ一覧取得

---

### 🤔 3つの違いをまとめると？

| 方法 | 用途 | HTTP メソッド | キャッシュ | 呼び出し方 |
|------|------|--------------|-----------|-----------|
| **サーバーコンポーネント** | 初期データ取得 | - | 自動 | `await prisma.*` |
| **サーバーアクション** | データベース更新 | POST のみ | `revalidatePath()` | `await updateDisplayName()` |
| **API Routes** | データ取得（特に外部API） | GET/POST/DELETE | 手動 | `await fetch('/api/*')` |

**このプロジェクトでの使い分け**:
```
認証チェック → サーバーコンポーネント (page.tsx)
   ↓
データ取得 → API Routes (/api/clips/favorites)
   ↓
データ更新 → サーバーアクション (actions/user.ts)
   ↓
UI更新 → クライアントコンポーネント (dashboard-content.tsx)
```

## 🛠️ 使用技術の詳細

### 1. Next.js 16 (App Router)

**理由**: React の最新機能（サーバーコンポーネント）を活用し、高速なWebアプリを構築

**メリット**:
- サーバーサイドレンダリング（SSR）で初期表示が高速
- ファイルベースルーティング（直感的）
- API Routes で簡単にバックエンド構築
- 画像最適化、コード分割などが自動

**デメリット**:
- 学習コストが高い（サーバー/クライアント分離の理解が必要）
- App Router は比較的新しく、情報が少ない場合がある

**使用箇所**: すべてのページ、API Routes

---

### 2. React 19

**理由**: UI をコンポーネントベースで構築、宣言的な記述が可能

**メリット**:
- コンポーネントの再利用性が高い
- 状態管理が直感的（useState, useEffect）
- 豊富なエコシステム

**デメリット**:
- フックの理解が必要
- パフォーマンス最適化（useCallback, useMemo）が複雑

**使用箇所**: すべての UI コンポーネント

---

### 3. TypeScript

**理由**: 型安全性を確保し、バグを事前に防ぐ

**メリット**:
- コード補完が効く（開発体験向上）
- 型エラーで間違いに気づける
- リファクタリングが安全

**デメリット**:
- 学習コストが高い
- 型定義の記述が増える

**使用箇所**: すべての .ts, .tsx ファイル

---

### 4. Prisma (ORM)

**理由**: TypeScript と相性が良く、型安全なデータベース操作

```typescript
// Prisma を使うと、型安全にDBアクセス
const user = await prisma.user.findUnique({
  where: { id: userId },
  include: { favoriteStreamers: true },
});

// user.name は自動的に string | null 型
```

**メリット**:
- SQL を書かずにデータベース操作可能
- 型定義が自動生成される
- マイグレーション管理が簡単

**デメリット**:
- 複雑なクエリは Raw SQL が必要な場合がある
- パフォーマンスチューニングが難しい場合がある

**使用箇所**: すべてのデータベース操作

---

### 5. PostgreSQL (Supabase)

**理由**: リレーショナルデータベースで、複雑なクエリに対応

**メリット**:
- 信頼性が高い
- Supabase で簡単にホスティング
- リアルタイム機能が統合されている

**デメリット**:
- NoSQL より柔軟性は低い
- スケーリングにコストがかかる

**使用箇所**: ユーザー情報、お気に入り配信者、いいねしたクリップ

---

### 6. NextAuth.js v5 (Auth.js)

**理由**: Next.js 専用の認証ライブラリで、簡単に実装可能

```typescript
// サーバー側で認証チェック
const session = await auth();
if (!session?.user) {
  redirect('/login');
}
```

**メリット**:
- 認証フローを簡単に構築
- セッション管理が自動
- 複数のプロバイダー対応（Google, GitHub 等）

**デメリット**:
- カスタマイズが複雑
- v5 は新しく、情報が少ない

**使用箇所**: すべての保護されたページ

---

### 7. Twitch Helix API

**理由**: Twitch のクリップデータを取得するため

**メリット**:
- 公式 API で信頼性が高い
- クリップ、配信者情報を取得可能

**デメリット**:
- Rate Limit がある（1分間に800リクエスト）
- OAuth トークンの管理が必要

**使用箇所**: クリップ取得、配信者検索

---

### 8. React Query (TanStack Query) v5 ✅ **実装済み**

**理由**: API 呼び出しのキャッシュ管理を自動化

```typescript
// React Query を使うと、キャッシュが自動管理される
const { data: clips, isLoading } = useQuery({
  queryKey: ['clips', 'favorites'],
  queryFn: async () => {
    const res = await fetch('/api/clips/favorites');
    return res.json();
  },
  staleTime: 5 * 60 * 1000, // 5分間キャッシュ
});

// お気に入り追加後、キャッシュを無効化
await queryClient.invalidateQueries({ queryKey: ['clips', 'favorites'] });
```

**メリット**:
- API 呼び出しの重複を防ぐ（同じデータを何度も取得しない）
- キャッシュが古くなったら自動で再取得
- ローディング状態の管理が簡単

**デメリット**:
- 学習コストが高い
- キャッシュの設定を誤ると古いデータが表示される

**使用箇所**: クリップ取得、お気に入り配信者取得

**実装状況**:
- ✅ package.json に追加済み（v5.62.11）

**効果**:

## 📂 ディレクトリ構造の理由

```
my-app/
├── app/                          # Next.js App Router
│   ├── dashboard/page.tsx        # ✅ サーバーコンポーネント（認証チェック）
│   ├── api/clips/route.ts        # ✅ API Routes（データ取得）
│   └── layout.tsx                # ルートレイアウト
│
├── components/                   # React コンポーネント
│   ├── dashboard/
│   │   ├── dashboard-content.tsx # ✅ クライアントコンポーネント（UI）
│   │   └── dashboard-sidebar.tsx
│   └── ui/                       # shadcn/ui コンポーネント
│
├── actions/                      # ✅ サーバーアクション
│   ├── user.ts                   # 表示名変更、アカウント削除
│   └── favorites.ts              # お気に入り追加/削除
│
├── hooks/                        # カスタムフック
│   └── use-dashboard-clips.ts    # クリップロジック分離
│
├── lib/                          # ユーティリティ・設定
│   ├── auth.ts                   # NextAuth 設定
│   ├── prisma.ts                 # Prisma Client
│   ├── twitch-api.ts             # Twitch API 関連
│   ├── constants.ts              # 定数管理
│   └── validations/              # バリデーション
│
├── types/                        # 型定義
│   ├── twitch.ts                 # Twitch 関連の型
│   └── database.ts               # DB types
│
└── prisma/                       # Prisma スキーマ
    └── schema.prisma             # データベーススキーマ
```

### なぜこの構造？

1. **app/ と components/ を分離**
   - app/ = ルーティング、認証チェック
   - components/ = 再利用可能な UI
   - 理由: 責務を分離し、保守性を向上

2. **actions/ ディレクトリ**
   - サーバーアクションを一箇所に集約
   - 理由: データベース更新処理を管理しやすくする

3. **hooks/ ディレクトリ**
   - カスタムフックでビジネスロジックを分離
   - 理由: コンポーネントをシンプルに保つ

4. **lib/ ディレクトリ**
   - 共通ユーティリティを一元管理
   - 理由: 重複コードを削減

5. **types/ ディレクトリ**
   - 型定義を一箇所に集約
   - 理由: 型の整合性を保つ

### 3. サーバーアクションでの二段階バリデーション

```typescript
// ✅ actions/user.ts
export async function updateDisplayName(name: string) {
  // 1. 認証チェック
  const session = await auth();
  if (!session?.user?.id) {
    return { success: false, error: 'Unauthorized' };
  }

  // 2. バリデーション
  const validation = validateDisplayName(name);
  if (!validation.success) {
    return { success: false, error: validation.error };
  }

  // 3. データベース更新
  await prisma.user.update({ ... });
}
```

**理由**: クライアント側のバリデーションは回避可能
